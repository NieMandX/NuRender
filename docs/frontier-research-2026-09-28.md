# Свежие исследования и проверка гипотез на M8

Срез литературы: **28 сентября 2026**. Продолжение [предыдущего обзора](rendering-research-2026-09-28.md).
Задача — статичная архитектурная сцена, прямой WebGPU, ограниченная память телефона.
В этом проходе добавлены воспроизводимые offline-эксперименты; формат рабочих сцен
и GPU-ядро 0.12 не менялись. Измеренного ускорения кадра этот отчёт не заявляет.

## Что нового в статьях

### 1. TexF / 3DNTC — текстура как поле на поверхности

[Beyond UV Mapping: Mesh Texture Compression via Surface-Aligned Texture Fields](https://arxiv.org/abs/2609.23606),
**20 сентября 2026**, препринт. Прочитаны метод и ограничения в [полном тексте](https://arxiv.org/html/2609.23606v1).

TexF хранит атрибуты в разреженных вокселях около поверхности; положения вокселей
восстанавливаются из меша. Для резидентного GPU-представления 3DNTC использует
квантованные хеш-признаки и небольшой нейросетевой декодер. Важен компромисс
между памятью и ошибкой изображения, включая стоимость декодирования при обращении.

Авторы показывают, что выигрыш зависит от числа текселей на грань: плотные сканы
часто выгоднее, а некоторые модели, созданные в DCC, эффективнее сохраняют UV.
Соседние тонкие поверхности могут смешивать атрибуты при грубой сетке вокселей;
полная функциональность обычной текстурной фильтрации пока отсутствует. PBR показан
как осуществимое расширение, а его всесторонняя оценка оставлена на будущее.

**Наш вывод:** интересный отдельный эксперимент для плотной декоративной геометрии.
Замена всех PBR-карт M8 пока не оправдана. Для стекла и стемолита ошибка блика
существенна даже при небольшом среднем цветовом отклонении. Обычное квантование UV
в эксперименте ниже — наш контрольный вариант, а не реализация TexF.

### 2. FA-QEM — упрощение с защитой особенностей формы

[Fast and Robust Mesh Simplification for Generated and Real-World 3D Assets](https://arxiv.org/abs/2605.14029),
**13 мая 2026**; на arXiv указан CVPR Workshop 3D4S 2026, не основной трек CVPR.
Прочитаны алгоритм и ограничения [полного текста](https://arxiv.org/html/2605.14029v1).

Основа QEM давно известна: ошибка вершины в однородных координатах равна
`Δ(v) = vᵀQv`; при схлопывании ребра квадрики его концов складываются.
FA-QEM дополняет оценку членами границ/кривизны и нормалей:
`Qgf = Qbase + Qboundary + Qnormal`, отдельно учитывая площадь в стоимости операции.
Позиция выбирается по `Qgf`; не следует приписывать алгоритму глобальный оптимум
полной составной функции. История схлопываний помогает переносить текстуру.

Ограничения существенны для M8: очень тонкие, переплетённые и самопересекающиеся
поверхности остаются трудными; эвристическое соединение разрывов способно ошибиться
на ограждениях, а перенос внешнего вида — перепутать близкие слои.

**Наш вывод:** кандидат для отдельного offline-сравнения фасадных деталей с meshoptimizer.
Защищать силуэт, проёмы и рёбра; не принимать уменьшение числа граней без проверки
формы и материалов. Нынешний meshoptimizer не является реализацией FA-QEM.

### 3. DJM — компактная основа и поле смещений

[DJM: Compact Base Meshes for Displacement Mapping using Triangle Jacobians](https://www.cs.ubc.ca/labs/imager/tr/2026/djm/),
**SIGGRAPH 2026**. Изучена страница авторов с описанием метода и результатами;
полный PDF здесь не анализировался. Код и данные на момент проверки помечены Coming Soon.

Подробную поверхность заменяют грубой сеткой и displacement-представлением.
При построении основы ограничивают искажение отображения через его якобиан,
сохраняя взаимно однозначное соответствие. Явное соответствие исходной и базовой
поверхностей позволяет избежать ненадёжного восстановления связей лучевыми пересечениями.

**Наш вывод:** перспективно для рельефа, лепнины и сложных сплошных деталей.
Для отдельных тонких стоек и стеклянных слоёв применимость нужно доказать отдельно.
Понадобятся новый экспорт и runtime восстановления поверхности; это существенно
больше, чем подключить один шейдер к текущим индексным буферам.

### 4. LOD-aware ReSTIR — сохранять световую историю при смене геометрии

[Real-Time Level-of-Detail Rendering with ReSTIR](https://research.nvidia.com/labs/rtr/publication/wang2026levelofdetail/),
**июль 2026, SIGGRAPH Conference Track**. Проверены метод и ограничения
в [PDF](https://research.nvidia.com/labs/rtr/publication/wang2026levelOfDetail/wang2026levelOfDetail.pdf).

Смена LOD меняет треугольники, поэтому прежняя адресация пути по номеру треугольника
теряет соответствие. Для неперекрывающихся UV авторы строят отображение
`τ = Φ₂⁻¹ ∘ Φ₁`; перекрывающиеся UV требуют дополнительного сопоставления.
Вес выборки корректируется якобианом — отношением локальных площадей:
`|Jτ| = |∂u x₂ × ∂v x₂| / |∂u x₁ × ∂v x₁|`.
Это позволяет повторно использовать световые пути между различными LOD.

Нужны согласованные UV, дополнительные структуры поиска и трассировочный путь.
Авторы тестировали Falcor на RTX 3090; эти результаты не подтверждают скорость
браузера на телефоне.

**Наш вывод:** сохранить ID экземпляров и соответствия поверхности при подготовке LOD
уже сейчас. Сам ReSTIR вводить после рабочего гибридного GI. Текущий растеризатор
от этой формулы автоматически быстрее не станет.

### Что отложено по результатам чтения

[Radiance Caching for Differentiable Path Tracing](https://rgl.epfl.ch/publications/Zhang2026Cache)
(SIGGRAPH/TOG, июль 2026) смешивает оценку из кэша с трассировкой через обучаемое
пространственное поле. Но задача работы — восстановление материалов и освещения
из наблюдений, то есть обратный рендеринг. Это потенциально полезно для будущего
подбора материалов по фотографиям, а не непосредственное ускорение нашего просмотра.

## Что проверено на нашей геометрии

Использованы текущие экспорты полной M8 и мобильной M8, проверены SHA-256 входных
файлов. Сводка результатов и хеши сохранены в [JSON](benchmarks/research-geometry-2026-09-28.json).
Исходный Blender-файл, рабочие экспорты и параметры материалов не изменены.

### Гипотеза A: искусственные границы частей мешают упрощению

Экспортёр режет меш на части до 20 000 треугольников. Мобильная подготовка упрощает
каждую часть с `LockBorder`. Проверили, поможет ли предварительное объединение
восьми соседних частей одного объекта/материала.

Для четырёх тяжёлых семейств взяты окна в начале, середине и конце: **96 частей,
1 894 363 исходных треугольника**. Объединение сваривает только полностью одинаковые
записи позиции, нормали и UV. Обе ветви используют один абсолютный предел ошибки
для всех частей окна, одинаковые веса атрибутов и целевой коэффициент 0.15.
Граница объединённой области тоже защищена; удаление отдельных компонентов отключено.

| Семейство, три окна | Отдельное упрощение, треугольников | После объединения | Изменение |
|---|---:|---:|---:|
| 184 — тёмный металл | 329 507 | 331 669 | +0,66% |
| 201 — тёмно-серый металл | 269 366 | 256 420 | −4,81% |
| 178 — белый алюминий | 203 029 | 201 544 | −0,73% |
| 43 — терракота | 348 084 | 336 232 | −3,40% |
| **Весь проверенный набор** | **1 149 986** | **1 125 865** | **−2,10%** |

В лучшем отдельном окне снижение составило 11,62%; в некоторых число граней выросло.
Это жадная оптимизация, поэтому больше свободы не гарантирует меньше граней.
Сообщённые упрощателем ошибки не превышают заданных пределов в обеих ветвях.
Однако его метрика — приближённая ошибка внешнего вида, не расстояние Хаусдорфа
и не гарантия ошибки в пикселях.

**Решение:** одно объединение исходных частей не является сильной оптимизацией всей M8.
На самой тяжёлой группе оно не дало выигрыша. Проценты этой выборки нельзя переносить
на всю сцену или трактовать как прирост FPS. Для внедрения всё равно потребуются
повторное разбиение под uint16 и визуальная проверка.

### Гипотеза B: уменьшить вершину с 20 до 16 байт

Текущая вершина: 8 байт позиции, 4 байта нормали и 8 байт UV. Квантование каждой
UV-компоненты в 16 бит в пределах части теоретически экономит **60 775 612 байт**:
17,12% от текущих 354 926 564 байт геометрии, до дополнительных параметров декодирования.

Проверены **все 962 части**. Оценка учитывает реальные UV, float32-округление
декодирования, матрицы Mapping материалов и размер мобильных текстур 256×256.
Для идеального квантования ошибка компоненты ограничена `range / (2 × 65535)`;
матрица Mapping переводит эту ошибку в текстурное пространство. В эксперименте
использованы максимумы ошибок восстановленных координат, а не только эта идеальная формула.

- Максимальная расчётная покомпонентная граница смещения — **18,7 текселя**.
- У 610 частей оценка превышает 0,25 текселя; у 223 — один тексель.
- В предел 0,25 попадают 352 части с потенциальной экономией только **19 229 988 байт**
  (5,42% всей геометрии), до служебных данных.

Некоторые материалы имеют огромный диапазон исходных UV. Более того, малая ошибка
выборки текстуры сама по себе не гарантирует сохранение производных UV и касательного
базиса normal map. Это вычислительная оценка кандидата, не сравнение готовых GPU-кадров.

**Решение:** единый UV16-формат для всех текущих частей отклонён. Возможны адаптивные
форматы или компактные пространственные страницы с меньшим UV-диапазоном, но переход
должен проверять также вырождение UV-треугольников, ориентацию и нормали.

## Какой следующий этап выбран

Наш инженерный приоритет после этих проверок — **пространственные страницы геометрии,
иерархия детализации и ограниченный резидентный набор**. Это сочетание известных методов,
а не заявление о новом математическом алгоритме.

Два семейства, 184 и 201, занимают 172 638 466 байт — 48,64% мобильной геометрии.
С них следует начинать пилот. Проверять новые представления всего леса сначала
невыгодно: значительная часть растительности уже использует общую геометрию экземпляров.

1. Группировать связанные поверхности и пространственно близкие детали внутри объекта
   и материала. Стабильно сохранять ID и UV; повторяющиеся детали проверять отдельно
   на возможность общего шаблона. Одно совпадение имени материала не доказывает повтор.
2. Подготовить несколько LOD с явной оценкой отклонения. Согласовать общие границы
   соседей; произвольная независимая децимация может открыть щели.
3. Выбирать уровень по экранной ошибке с гистерезисом. Ориентир:
   `errorPixels ≈ errorWorld × focalLengthPixels / distanceToBounds`.
   У near plane, тонких деталей и изменившегося силуэта нужна более консервативная оценка.
4. Подгружать и вытеснять страницы по бюджету памяти. Грубый предок остаётся видимым,
   пока детальный уровень полностью не готов. Не держать все уровни одновременно.
5. Измерять холодный старт, пиковую память и время кадров на тех же камерах.
   Проверять силуэты, проёмы, стыки, блеск и normal maps. Объём файла в облаке
   и количество выделенной GPU-памяти учитывать отдельно.

Для статичных теней сохраняется отдельное постоянное представление отбрасывателей:
переключение видимой камерой детализации не должно само по себе перестраивать тень
или исключать невидимые камерой объекты из неё. Улучшение фильтрации тени оценивается
по качеству и стоимости выборок; экономии от устранения повторной постройки у нас
уже нет, поскольку карта кэшируется.

Постоянное представление отбрасывателей тоже входит в бюджет памяти. Для фиксированного
солнца можно исследовать загрузку заранее подготовленной карты глубины и освобождение
подробной геометрии после подготовки. Изменение света или состава непрозрачных
поверхностей требует явной инвалидации; хранить всю детальную M8 ради возможной
перестройки тени на мобильном устройстве не следует.

После геометрии: сравнить предварительно рассчитанный непрямой свет и гибридный
режим с одним отскоком. Для неподвижной камеры допустимо ограниченное накопление
до заданного качества с последующим сном GPU. ReSTIR — следующий отдельный опыт,
не предварительное условие для быстрого мобильного просмотра.

Это ещё не подтверждение работы на физическом телефоне: desktop-профиль mobile
не воспроизводит память, тепловой режим и драйверы Android/iOS.

## Воспроизведение

При наличии локальных экспортов `m8-full` и `m8-mobile`:

```sh
node scripts/research-geometry.mjs /private/tmp/nurender-geometry-research.json
```

Скрипт только читает модель и записывает отчёт в указанный путь. Времена упрощения
в полном JSON — диагностические offline-замеры, не benchmark runtime и не устойчивое
сравнение скорости алгоритмов. Файлы готовой сцены не перезаписываются.
