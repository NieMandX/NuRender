# NuRender / Structured Renderer 0.5

Локальный исследовательский стенд прямого WebGPU / WGSL. Проверяет стоимость
разных представлений одной геометрии. Это не доказательство нового алгоритма
рендеринга: основа — растеризация, инстансинг и параметрическое хранение.

## Запуск

```sh
npm install
npm run dev -- --host 127.0.0.1
npm run build
npm test
```

Адрес берётся из вывода Vite (в текущей сессии `http://127.0.0.1:5174/`).
`?scene=blender` сразу загружает реальный экспорт. Исходники сторонних проектов
и открытая сцена Blender не изменяются. Нужен WebGPU; ошибки API/адаптера
выводятся в интерфейсе. ЛКМ — вращение, колесо — масштаб, 1/2/3 — режим.

## Пакетная отрисовка и материалы элементов (0.5)

В реальной сцене B по умолчанию использует **пакетную** отрисовку. Переключатель
«Отрисовка → По шаблону» сохраняет реализацию 0.4 для сравнения на той же сцене.
Все 222 семейства повторяющихся частей собраны в один indexed draw на проход;
39 остальных мешей/остатков идут обычным путём. Итого **80 команд вместо 522**
на shadow + color; C использует 78. Количество треугольников осталось 675 408.

`src/batch.ts` упаковывает 9 509 уникальных вершин шаблонов и 2 624 записи
элементов. Каждый uint32 индекс содержит 16 бит адреса вершины и 16 бит
адреса элемента. WGSL `vsBatch` читает эти адреса через vertex_index, затем
выбирает вершину, матрицу и материал из storage buffers. Повторяются индексы,
не вершины. Индексный поток содержит 117 063 угла треугольников. Деревья и
крупные остатки не разворачиваются в этот поток. Это vertex pulling с таблицей
элементов, а не утверждение о научной новизне.

Одна запись элемента: исходные 28 float32 матриц плюс четыре uint32 —
**element ID, material ID, family ID, номер копии**. ID элемента устойчив в
пределах одного разбора; после нового экспорта/разбора он может измениться.
Материал 0 оставляет исходный RGB. Зарезервирован отдельный слот материала
для каждого элемента: цвет/вес замещения и коэффициент emissive, 32 байта.
Назначение всей группе меняет слоты её копий; индивидуальное назначение
перезаписывает только выбранную копию. Геометрия и число draw calls от этого
не меняются. Данная версия ограничена 65 536 вершинами и элементами в одном
пакете; превышение обнаруживается с ошибкой, автоматическое разбиение на
несколько пакетов ещё не сделано.

### Как проверить материалы

1. В панели «Материал элемента · B» выбрать группу (по умолчанию #31).
2. Выбрать «Всей группе» или «Одной копии», задать цвет и свечение.
3. Нажать «Применить в B»: включится пакетный B, камера приблизится к группе.
4. «Сбросить материалы» восстановит оригинал и снова разрешит бенчмарк.

Это настройка параметров одного WGSL-шейдера, **не редактор произвольных
шейдерных программ**. Цвет UI переводится из sRGB в linear. Emissive добавляется
к цвету поверхности; нет bloom, GI или освещения соседних объектов. Нет UV,
текстур, прозрачности, PBR roughness/metalness. Пока доступны найденные повторяющиеся
части; уникальный остаток этим интерфейсом не редактируется. Изменения временные,
до перезагрузки; сохранение/импорт наборов материалов пока отсутствует.

A/C и старый B сохраняют исходные материалы. При наличии назначений переключатель
на старый B и бенчмарк заблокированы; сброс снимает блокировку. Диагностическая
окраска временно скрывает материал и также блокирует замеры. Обычные A/C можно
просматривать для сравнения с исходником. В процедурной сцене панель скрыта.

### Контроль 0.5

Встроенный браузер, Apple metal-3, canvas 1140×900, общий вид, 27.09.2026.
Материалы сброшены, по 120 измерений на режим. Два последовательных прогона
при одинаковой камере: пакетный и старый B. Это контроль на одном GPU, не
доказательство универсального ускорения.

| Метрика | B пакетный | B по шаблону | C (пакетный прогон) |
|---|---:|---:|---:|
| GPU median, мс | 2,425 | 2,490 | 2,425 |
| CPU submit median, мс | 0,300 | 0,400 | 0,300 |
| GPU p95, мс | 2,621 | 3,080 | 3,146 |
| Команд shadow + color | 80 | 522 | 78 |
| Буферы сцены, МиБ | 12,92 | 12,41 | 15,36 |
| Отличающиеся от A пиксели | 55 / 1 026 000 | 62 / 1 026 000 | 0 |

Пакетный B занимает 13 549 592 байта, экономия относительно C — **15,9%**.
Адресный поток и таблица материалов увеличили память относительно старого B
на 537 548 байт. Отдельные batch buffers занимают 1 268 484 байта. Стенд
сохраняет обе реализации B для переключения, поэтому residentSceneBuffers =
28 044 272 байта вместе с процедурным кэшем; CPU typed arrays = 24 124 676 байт
плюс JS-объекты и временные аллокации. Это не полная VRAM. allocationBreakdown
показывает резидентные группы; BBatch/старые шаблоны не следует одновременно
суммировать как размер только активного B (поле bytesB уже рассчитано отдельно).

Пакетный B пока сравнялся с C по GPU-медиане данного прогона, а не доказал
превосходство. Количество draw calls уменьшено достоверно. Изображение B не
побитово одинаково: для пакетного пути max RGB delta = 161/255,
MAE = 0,001770/255. Причины могут включать float32 и порядок перекрывающихся
треугольников; малую долю изменённых пикселей нельзя трактовать как нулевую
ошибку. C/A совпадают побитово.

Проверки 0.5: декодирование каждого batch-индекса сверено с вершиной/матрицей
старого B; проверены ID, переполнение адресов, точечное/групповое назначение,
сброс без изменений геометрии и число команд/треугольников. Всего 18 тестов.
В браузере проверены реальные материалы всей группы и одной копии, сброс,
блокировка бенчмарка, два завершённых прогона, desktop 1440×1000 и mobile
390×844. Горизонтального переполнения и ошибок/предупреждений приложения нет.

## Два эксперимента, разные значения A/C

### Процедурная сцена: сильный baseline

16–1024 здания, 1/4/16 шаблонов с разными этажностью, пропорциями и фасадами.
У каждого здания есть собственные козырёк и вывеска. Три ручных уровня LOD
применяются одинаково ко всем представлениям.

| Режим | Хранение и отрисовка |
|---|---|
| A · Детали | Общий куб, плоский массив трансформаций всех деталей всех зданий |
| B · Структура | Общий куб, шаблон деталей на каждый тип, параметры зданий; vertex shader восстанавливает деталь |
| C · Меши | Обычный индексированный меш целого здания на каждый тип; стандартный инстансинг зданий |

C — полноценный второй baseline, а не ещё один вариант B: позиции его вершин
запечены на CPU, нет декодирования деталей в шейдере. Цвет и tint-selector
хранятся в вершинах. Это обычная float32/indexed реализация без квантования
нормалей или mesh compression, а не утверждение об оптимальности baseline.

Уникальные детали и основание общие для A/B/C и включены в каждый расчёт
буферов. Геометрия, свет, камера, тени, число треугольников совпадают.
Размеры процедурных деталей кратны 1/64, масштабы кратны 1/8: это устраняет
разницу float32 из-за порядка арифметики между запечённым и параметрическим
представлениями. Это свойство тестовой сцены, не обещание побитового совпадения
для произвольных входных координат.

### Реальная сцена: Blender / M8

Экспорт из открытого `M8_new_PBR_flow.blend`: область 100 × 100 м вокруг
выделенной баскетбольной площадки. 67 объектов, 39 уникальных групп геометрии,
675 408 треугольников после точной обрезки границы. Среди них 29 экземпляров
одного общего меша дерева. Исходная сцена содержит 265 меш-объектов;
архитектура преимущественно объединена по материалам.

| Режим | Что проверяется |
|---|---|
| A · Объекты | Отдельный drawIndexed для каждого объекта; mesh-буферы уже разделяются |
| C · Инстансы | Один instanced drawIndexed на каждую общую группу mesh + material |
| B · Повторы | Выделенные шаблоны частей + массивы переносов + компактный уникальный остаток |

В реальном эксперименте A и C используют **те же физические GPU-буферы**.
Поэтому экономии хранения между ними нет: проверяется именно уменьшение
количества draw calls. Не следует сравнивать смысл метки A между двумя
экспериментами. В JSON есть source, supportedModes и пояснение метода;
B имеет отдельное представление геометрии; его размер включает общие с A/C нетронутые меши.

Экспортёр `scripts/export_blender_fragment.py` читает mesh datablocks,
трансформации и базовые цвета материалов. Не вызывает операторов сохранения,
не меняет объекты, материалы или выделение. Обрезка выполняется в памяти;
граничные треугольники перетриангулируются, внутри области нет decimation.
Формат в `public/scenes/m8-fragment/` — manifest + бинарные vertex/index
буферы, не универсальный GLB/FBX importer. Полный исходный `.blend` не копируется.

**Визуальные ограничения реального примера:** текстуры, прозрачность,
alpha-cutout листвы, сложные материалы и smooth/split normals не перенесены;
используются базовые цвета, непрозрачные поверхности и плоские нормали.
Сравнение качества A/C относится к этому общему упрощённому отображению,
а не к совпадению изображения с Blender.

## Поиск повторений (0.3)

В Blender-сцене нажмите **«Показать повторения»**. «Все группы» окрашивает
повторяющиеся части, «Одна группа» позволяет выбрать ID и приблизить её.
«Исходная» возвращает оригинальные цвета. Серый цвет означает остаток либо
исключённую геометрию. Цвета помогают осмотру; близкие оттенки разных групп
не означают совпадение — точный выбор выполняется по ID. Геометрия и индексы
не заменяются. Бенчмарк блокируется при диагностической окраске.

Предварительный разбор запускается командой `npm run analyse` (Node + tsx,
без Blender и новых зависимостей). Браузер загружает готовый результат,
а не выполняет поиск заново. Исходные vertex/index файлы не изменяются.

Метод в `src/repetitions.ts`:

1. Перевод координат в метры сцены и объединение вершин по позиции в сетке
   0,1 мм, чтобы соединить разрывы flat shading; поиск связных компонентов.
2. Нормализация переносом к минимуму bounding box; сравнение отсортированных
   ориентированных треугольников с учётом нормалей и цвета.
3. Сигнатура с шагом 1 мм предлагает совпадение. Отдельная проверка каждого
   соответствующего угла треугольника ограничивает евклидову ошибку 1 мм,
   а разницу атрибутов — 1e-4. Обратный winding не считается совпадением.
4. Семейство принимается от 3 копий; компонент должен содержать минимум
   4 треугольника и иметь размер хотя бы 0,2 м по одной оси.

Поиск идёт **внутри отдельных мешей с одним экземпляром**, без вращения,
масштаба, объединения нескольких материалов и семантического распознавания.
Связные поверхности не разрезаются на окна автоматически. Округление может
пропустить близкие совпадения на границах сетки. Пересекающиеся/касающиеся
детали могут объединиться. Обрезанные границей фрагмента детали часто не
совпадают с целыми. Это консервативная начальная выборка, не оценка всех
возможных повторений и не доказательство новизны рендера.

Результат текущего экспорта:

| Показатель | Значение |
|---|---:|
| Исследовано треугольников | 146 384 |
| Исключено (деревья, включая уже инстансированные) | 529 024 |
| Найдено семейств / экземпляров частей | 222 / 2 624 |
| Треугольников в найденных повторениях | 39 021 |
| Доля исследованной геометрии / всей сцены | 26,66% / 5,78% |
| Подготовка, один локальный запуск | около 477 мс |

Это **не процент экономии памяти или ускорения**. Среди семейств есть
простые стойки ограждений и элементы площадок. Пример фасада: #31 — 40
стеклянных частей по 18 треугольников, #94 — 98 окрашенных частей по 12.

`repetitions.json` содержит ID, исходный объект и группу, списки треугольников,
переносы относительно первой копии, bounds, максимальную ошибку, SHA-256
исходного manifest + бинарной геометрии и статистику. `*.families.bin` —
uint32 ID семейства для каждой вершины (0 = остаток/исключённая геометрия).
После нового экспорта обязательно повторить `npm run analyse` и `npm test`;
проверка sourceDigest обнаруживает устаревший разбор. Начиная с 0.4 браузер
тоже вычисляет SHA-256 исходного manifest + всех vertex/index буферов перед
созданием B и отклоняет несовпадающий разбор.

Окраска перезаписывает только RGB в GPU-буферах текущих представлений;
отдельных диагностических GPU-буферов нет. На CPU сохраняются исходные vertex-буферы и карты
семейств (`realSceneCpuBufferBytes` в метриках), плюс JS-отчёт. При переключении
возникает временная копия одного vertex-буфера. Это диагностические расходы,
не размер только B. В 0.4 также кэшируются CPU-данные новых шаблонов и остатков. Сброс камеры возвращает весь фрагмент;
JSON бенчмарка включает framing, чтобы зафиксировать приближение к семейству.

Новые тесты независимо сверяют координаты всех опубликованных копий,
атрибуты, отсутствие пересечения списков треугольников, карты ID, sourceDigest
и статистику. Синтетические тесты проверяют перестановку индексов, flat-shading
разрывы, изменённую форму/цвет/winding и минимум копий. Тест записей GPU-буферов
проверяет изменение только RGB и побайтовое восстановление исходных данных.

## Измерения

- A/B/C/C/B/A для обеих сцен (с версии 0.4).
- 30 кадров прогрева + 60 измерений на этап, 120 замеров на режим.
- Камера, разрешение и параметры блокируются. Уход вкладки в фон или resize
  отменяет прогон. После изменения камеры/сцены/разрешения результат сбрасывается.
- CPU submit — кодирование, запись uniform и submit; не время выполнения GPU.
- GPU — сумма shadow и color passes через timestamp-query, если поддерживается.
  [API timestampWrites](https://gpuweb.github.io/types/interfaces/GPURenderPassTimestampWrites.html).
- RAF/FPS включает vsync, браузерное планирование и ожидание readback timestamps.
  Это не показатель неограниченной пропускной способности GPU.
- Прямое сравнение RGB-пикселей A/B и A/C после измерений, с max/MAE/долей
  отличающихся пикселей. Экспорт JSON содержит исходные выборки и p95.
- Буферы — явные аллокации геометрии/инстансов. Это **не полная VRAM**.
  Альтернативы и загруженный реальный фрагмент кэшируются одновременно;
  residentSceneBuffers включает эти кэши. Uniform, 16 МиБ shadow texture,
  depth и внутренние аллокации драйвера не входят в per-mode scene buffers.
- На простое нет бесконечного render loop. Автоматического LOD/culling, GI,
  спектральной и волновой оптики в этой версии нет.

## История: исполняемое разложение B (0.4)

`src/structured-real.ts` собирает по одному индексированному мешу на семейство
и 28 float32 на экземпляр (матрица и матрица нормалей, общий формат с A/C).
Переносы добавляются к translation исходной матрицы объекта. Уникальные
треугольники собираются в компактный остаток с исходными атрибутами.
Группы без найденных повторений, включая деревья, используют те же физические
GPU-буферы, что A/C. Каждый треугольник представлен ровно один раз;
суммарно остаётся 675 408 треугольников.

**Это обычный инстансинг автоматически выделенных подмешей**, тот же шейдер
`vsReal`, а не новый способ растеризации и не параметрическое декодирование
процедурного B. На этой ступени проверяется полезность разложения геометрии.
Создание B автоматически происходит при загрузке Blender-сцены. Поиск повторений
выполнен заранее, его ~477 мс не входят в время упаковки B или GPU кадра.

Кэш стенда сохраняет A/C, B и процедурную сцену одновременно. На текущем
фрагменте: A/C 16 110 640 байт, B 13 012 044 байт (−19,23%). Из B
6 229 608 байт физически общие с A/C; дополнительно выделено 6 782 436 байт.
Весь residentSceneBuffers стенда — 26 775 788 байт, не включая текстуры,
uniform и драйвер. CPU typed arrays занимают 22 818 156 байт плюс JS-отчёт,
временные данные упаковки и хеширования. После загрузки исходные index arrays
и объединённый буфер для SHA-256 доступны сборщику мусора.

Контрольный прогон: встроенный браузер, Apple metal-3, canvas 1140×900,
27.09.2026, порядок A/B/C/C/B/A, по 120 измерений на режим.

| Метрика, общий вид | A | B | C |
|---|---:|---:|---:|
| GPU median, мс | 2,490 | 2,294 | 2,228 |
| GPU p95, мс | 2,621 | 2,556 | 2,556 |
| CPU submit median, мс | 0,200 | 0,300 | 0,300 |
| Буферы, МиБ | 15,36 | 12,41 | 15,36 |
| Draw calls, shadow + color | 134 | 522 | 78 |
| Отличающиеся от A пиксели | — | 62 / 1 026 000 | 0 |

Упаковка B с созданием/записью GPU-буферов заняла 27,3 мс на CPU в первом
запуске; не включает загрузку сети, SHA-256, заранее выполненный поиск или
ожидание завершения GPU. На крупном плане через «Приблизить группу #31»:
GPU median A/B/C = 3,015 / 2,818 / 2,753 мс; B/A отличается на 24 пикселях,
C/A побитово совпадает.

Это два вида на одном GPU, не статистически доказанное ускорение. B пока
**не быстрее сильного baseline C**. Число команд выросло до 261 на проход:
222 семейства плюс исходные/остаточные меши. Следующий эксперимент —
пакетирование отрисовки шаблонов, а не объявление выигрыша по одному GPU-замеру.

Изображение B не побитово эквивалентно A: максимальная разница RGB-канала на
общем виде 156/255, MAE 0,001987/255; на фасаде 152/255 и 0,000497/255.
Малое число изменённых пикселей не означает малую ошибку каждого из них.
Меняются порядок треугольников и арифметика float32; в исходной сцене есть
перекрывающиеся поверхности. Вклад каждого фактора отдельно не измерен.
Тест с независимым восстановлением координат даёт максимум 0,0484 мм при
раздельных float32 операциях; GPU может применять FMA, поэтому это не предел
ошибки пикселей. Уникальные остатки сохраняют исходные атрибуты побитово.

Дополнительные проверки: все принятые копии восстановлены в пределах допуска,
нет потерь/дублирования треугольников, неправильные ID и перекрытия отклоняются,
окраска B меняет только RGB и восстанавливает буферы побайтово. Устаревший
sourceDigest останавливает загрузку с объяснением; уже выделенные буферы
освобождаются. Бенчмарк недоступен при диагностической окраске.
