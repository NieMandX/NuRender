# Следующие алгоритмы NuRender — 28 сентября 2026

Цель: статическая архитектурная сцена в браузере телефона/планшета. Приоритеты —
память и время первого изображения, затем время кадра, затем дополнительные эффекты.
Это выбор направлений для экспериментов, а не заявление о превосходстве над другими движками.

## Что дают работы 2023–2026 годов

| Работа / первичный источник | Полезная идея | Применимость к NuRender |
|---|---|---|
| [Towards Practical Meshlet Compression, 2024](https://arxiv.org/abs/2404.06359) | Оптимизация полос треугольников через MILP, параллельное декодирование meshlet, квантование без трещин. | Заимствовать согласованное квантование границ и компактные пространственные части. Реализация авторов использует mesh shader; её скорость на RX 7900 XTX нельзя переносить на WebGPU телефона. |
| [Seamless Rendering on Mobile / NanoMesh, SIGGRAPH 2024](https://advances.realtimerendering.com/s2024/content/Cao-NanoMesh/AdavanceRealtimeRendering_NanoMesh0810.pdf) | Иерархия кластеров, загрузка от грубых уровней к подробным, HZB, отсечение и выбор LOD по экранной ошибке. | Самое близкое направление: начать с грубой полной сцены и догружать только нужную детализацию. Visibility buffer — отдельная гипотеза, требующая замера стоимости памяти и проходов. Это доклад о нативном мобильном рендере, не готовая библиотека для браузера. |
| [Aaltonen / HypeHype, SIGGRAPH 2023](https://advances.realtimerendering.com/s2023/AaltonenHypeHypeAdvances2023.pdf) | Уменьшать обмен с общей памятью и число сохранений render targets; учитывать цену произвольных SSBO-загрузок на мобильных GPU. | Сохранять простой indexed raster как контроль. Прежде чем переносить всё в compute, сравнить суммарное время и нагрев. Ограничения оборудования в докладе описывают 2023 год; возможности конкретного устройства проверяются отдельно. |
| [ReSTIR PT Enhanced, I3D 2026](https://research.nvidia.com/labs/rtr/publication/lin2026restirptenhanced/) | Взаимный выбор соседей сокращает работу пространственного переиспользования; footprint-based reconnection и карты дублирования улучшают устойчивость выборок. | Перспективно после появления трассировки и корректной истории кадров. Указанное авторами ускорение 2–3× относится к их ReSTIR PT, а не ко всему рендеру и не к телефонам. |

Дополнительный ориентир для освещения — [RTXGI / SHaRC](https://github.com/NVIDIA-RTX/RTXGI):
пространственный хеш-кэш освещённости без обязательных Tensor Cores. Пример SDK использует
DX12/Vulkan и требует DXR-совместимый GPU для SHaRC; это не готовый WebGPU-модуль.
Для нас интересна организация переиспользования освещения, а не перенос всего SDK.

Текущий [стандарт WGSL](https://gpuweb.github.io/gpuweb/wgsl/#shader-stage) определяет
vertex, fragment и compute стадии. В нашем браузерном пути нет native mesh shader / ray tracing pipeline.
Экспериментальная трассировка потребует собственного обхода BVH в compute.

## Что уже внедрено, а что ещё нет

В 0.11 внедрены стандартные методы: кэш статичной shadow map, подготовленное GGX-окружение,
meshopt, отдельный упрощённый мобильный экспорт, ограничение пикселей, освобождение CPU-геометрии
и неактивной импортированной сцены. Path tracing и глобального освещения от геометрии пока нет.

В 0.12 добавлены загрузка ресурсов с отдельного origin, ограниченный prefetch и переключаемое
консервативное frustum culling. Последнее — давно известный базовый алгоритм, не математическая новинка.
Проверка отсечения выполняется на CPU; крупные частично видимые пакеты всё ещё рисуются целиком.
Видимость кэшируется для неподвижной камеры. Отбрасыватели теней не отсекаются по камере.
HZB, GPU indirect compaction, кластерная иерархия и потоковый LOD ещё не внедрены.

## Следующий эксперимент: первый кадр и память

Существующий мобильный экспорт всё ещё содержит 9.13 млн треугольников и около 355 МБ
GPU-буферов сцены. Хранение в облаке решает доставку, но не уменьшает этот объём на устройстве.

1. Сделать грубую полную геометрию для первого кадра и независимые пространственные страницы
   подробностей. Сохранить ID объектов, материалов и границы примыкания частей.
2. Выбирать уровень по проекции геометрической ошибки: приближённо
   `errorPixels = errorWorld * focalLengthPixels / distanceToBounds`.
   Добавить гистерезис, чтобы небольшое движение камеры не вызывало постоянных переключений.
3. Ограничить резидентный набор страниц бюджетом GPU-памяти; вытеснять ненужные подробности,
   оставляя грубого предка. Сначала полностью загрузить новый уровень, затем переключить его.
4. Сравнить загрузку, пиковую память и силуэт на одинаковых камерах. Не принимать экономию,
   если возникают дырки, пропавшие элементы или скачки важных фасадных деталей.

Параллельно проверить KTX2/Basis для текстур с выбором поддерживаемого GPU-формата. Уменьшение
PNG по сети само по себе не уменьшает RGBA/mip-память после декодирования.

## Освещение после оптимизации геометрии

Для статичной сцены выгодно вынести диффузный непрямой свет в предварительно рассчитанные
lightmaps или probes. Это наше инженерное предположение: проверить утечки света, стоимость
хранения, изменение ручных материалов и отличие от контрольного offline-кадра.

Первый эксперимент с трассировкой предлагается ограничить одним непрямым отскоком:

- Растеризация даёт первичную видимость, глубину и нормаль. Прямой свет сохраняет готовую тень.
- Статичный BVH строится заранее. Упрощённая геометрия для лучей сравнивается с полной по утечкам.
- Вторичные лучи считаются в пониженном разрешении; шум подавляется фильтром с учётом глубины
  и нормалей. Проверяются тонкие элементы, стекло и границы объектов.
- При неподвижной камере допускается ограниченное накопление сэмплов, затем GPU засыпает.
  При изменении камеры, материалов, света или геометрии история сбрасывается либо валидируется.
- ReSTIR и пространственный radiance cache добавляются только после измеренного базового пути.

Это гибридный рендер с ограниченным GI, не обещание полного path tracing в реальном времени
на любом телефоне. Для зеркального стекла и нескольких переотражений нужен отдельный бюджет.

## Как подтверждать преимущество

На физических Android/iPhone/iPad: одинаковые камера, разрешение и качество; время первого
изображения с холодным кэшем, память, p50/p95 кадра, десятиминутная навигация и возврат из фона.
Сначала сравнивать с предыдущей версией NuRender. С Three.js/Babylon.js сравнивать только после
подготовки эквивалентных сцен, света, теней и настроек качества. Размер бандла, draw calls
или скорость чужой статьи по отдельности не доказывают преимущество.
